Chapter 1

Project Setup with Swift Package Manager

We're going to build DepDeck: a real macOS menu bar app that tracks every CLI tool you've installed with Homebrew, npm, and cargo — showing updates, flagging deprecated packages, and offering one-click replace or delete.

Surprise number one: you don't need Xcode. The Swift Package Manager (SPM) ships with the Swift toolchain and can build full apps from a folder containing one manifest file. Create the skeleton:

$ mkdir -p ~/Developer/DepDeck/Sources/DepDeck/{Managers,Views}

Now the manifest. Click the highlighted lines in any code block to see why they matter:

The minimum macOS version. MenuBarExtra (our menu bar scene) needs macOS 13+; we use 14 for the modern onChange API. This does not mean "only runs on 14" — it means "at least 14".
.executableTarget produces a runnable binary. Libraries use .target instead. Every .swift file under path gets compiled into this target automatically — no file lists to maintain.
💡 Swift Concept — Packages, Targets, Products

A package is a folder with a Package.swift. It contains targets (groups of source files that compile together). An executableTarget named DepDeck means swift build produces .build/debug/DepDeck — an actual runnable program.

Chapter 2

Modeling the Domain — Structs & Enums

Before any UI or shell commands, answer the question: what is a package? In Swift you model data with structs (value types) and enums (closed sets of cases). Start with the three package managers:

Three protocols at once: String gives each case a raw value ("brew"…), CaseIterable adds an automatic allCases array for looping in UI, and Identifiable lets SwiftUI lists tell items apart.
A computed property — it stores nothing and runs on every access. The switch must be exhaustive: add a fourth case to the enum and the compiler forces you to handle it here. That's Swift's biggest safety win over passing strings around.

Now the star of the show — one struct that represents a package from any manager:

let = immutable after creation, var = mutable. Identity fields (which manager, what name) can never change, so they're let.
String? is an Optional: "a String or nothing." Swift forces you to unwrap it before use — there are no surprise null crashes like in many other languages.
String interpolation \(…) builds "brew:ripgrep". Combining manager + name means the same tool installed via two managers won't collide in a SwiftUI list.
?? is the nil-coalescing operator: use the left value unless it's nil, otherwise the right. Disabled is more severe than deprecated, so its reason wins.
💡 Swift Concept — Value Types

Structs are copied on assignment, not shared. Hand a Package to a view and the view gets its own copy — nobody can mutate it behind your back. Shared mutable state will live in exactly one place: the Store (Chapter 6).

Chapter 3

Running Shell Commands with async/await

DepDeck is fundamentally a friendly UI over brew, npm, and cargo. So we need one rock-solid primitive: run a command, give me its output, or throw a useful error. First, the error type:

An enum case with associated values — payload data attached to the case. This is how Swift models "an error plus its context" without stringly-typed exceptions.
Conforming to LocalizedError and implementing errorDescription means error.localizedDescription anywhere in the app shows our friendly message — which we surface in the UI's error banner later.

Now the workhorse. Process is Apple's API for spawning child processes, but it's callback/blocking-based. We bridge it into async/await:

An enum with no cases can never be instantiated — Swift's idiom for a pure namespace of static functions.
@discardableResult silences the "result unused" warning when callers run something like brew update and don't care about the output text.
async throws -> String means callers write let out = try await Shell.run("…"). await marks where the caller may suspend; try marks that it can fail.
The bridge between callback-world and async/await-world. You receive a continuation; call resume(returning:) or resume(throwing:) exactly once and the caller's await completes. "Checked" means the runtime yells at you if you resume twice or never.
zsh -lc runs the command through a login shell, which loads your ~/.zprofile — so the user's real PATH (/opt/homebrew/bin, ~/.cargo/bin…) applies. A bare Process has a minimal PATH and would not find brew at all.
⚠️ The classic deadlock: a pipe buffer holds ~64KB. If the child writes lots to stderr while we're only reading stdout, the child blocks waiting for stderr to drain — and we block waiting for stdout to end. Forever. Reading the two pipes on separate queues fixes it. Every CLI-wrapping app hits this bug eventually; ours is pre-fixed.
Convention: exit status 0 = success, anything else = failure. We throw our typed ShellError with stderr attached so the UI can show why the command failed.

Chapter 4

The Homebrew Client — JSON with Codable

Homebrew can describe every installed formula as JSON — including the fields that power our killer feature:

$ brew info --json=v2 --installed { "formulae": [ { "name": "wget", "outdated": false, "deprecated": false, "deprecation_reason": null, "deprecation_replacement_formula": null, … } ] }

Swift's Codable system turns JSON into typed structs with zero hand-written parsing. Declare structs whose property names match the JSON keys:

private because this struct mirrors brew's messy external format. The rest of the app only ever sees our clean Package model — this is the adapter pattern.
Nested JSON objects become nested structs. "versions": {"stable": "1.2"} decodes into Versions automatically.
We keep snake_case property names so they match the JSON keys exactly with no extra configuration. (Alternative: decoder.keyDecodingStrategy = .convertFromSnakeCase and camelCase names.)
The payoff field: when brew deprecates a formula it often names a successor. This single optional string powers the "Replace with X" button in Chapter 9.

Decoding and mapping into our domain model:

One line replaces hundreds of lines of manual JSON walking. If the JSON shape doesn't match the structs, decode throws a precise error naming the missing key.
compactMap = map plus drop nils. Any formula we return nil for simply vanishes from the result.
guard let unwraps an optional or exits early — Swift's "keep the happy path un-indented" tool. installed.last?.version uses optional chaining: if the array is empty, the whole expression is nil.
A chain of ?? picks the first non-nil replacement suggestion, preferring the more severe "disabled" replacement over the "deprecated" one.

The rest of the client is one-liners delegating to Shell.run: brew install '\(name)', brew upgrade, brew uninstall, and brew search --formula whose output we split into lines for search results.

Chapter 5

npm & cargo — Defensive Integration

Same adapter pattern, two new flavors of "real-world tools are quirky."

Quirk #1: npm exits 1 on purpose

npm outdated -g --json exits with code 1 whenever anything is outdated — that's by design. Our Shell.run would throw, so we defuse it:

Two safety nets stacked: || true makes the shell command always exit 0, and try? converts any remaining thrown error into nil, which ?? "{}" turns into an empty JSON object. "This is allowed to fail" — expressed in types.
npm's deprecation check: the command prints the deprecation message only if the package is deprecated, otherwise nothing. An empty result = healthy package.

Quirk #2: cargo speaks plain text

No JSON available for installed crates — we parse cargo install --list, whose format is "name vX.Y.Z:" lines followed by indented binary names:

Two conditions in one guard, comma-separated (both must pass). Indented lines and non-header lines get skipped with continue.
dropLast() trims the trailing :; dropFirst() below strips the v prefix from v14.1.0. Swift string slicing returns cheap views — wrap in String(…) to materialize.

Latest versions come from the crates.io HTTP API. Async/await makes a network request feel like a function call:

crates.io's API policy asks every client to identify itself with a User-Agent. Be a good API citizen — anonymous traffic may get blocked.
One awaited line: send the request, suspend without blocking any thread, resume with (Data, URLResponse). The tuple's second element is ignored with _.

Chapter 6

The Store — Observable State

Every screen needs the same data: the package list, what's busy, the last error. That shared mutable state lives in exactly one object — the store — and SwiftUI observes it.

@MainActor guarantees every property access and method runs on the main thread — the only thread allowed to drive UI. The compiler enforces this; background code must await its way in.
A class, not a struct: many views must share one instance. ObservableObject is the protocol that lets SwiftUI subscribe to it.
@Published = "when this changes, re-render every view that reads it." That single line is the entire UI-update mechanism.
@AppStorage reads/writes UserDefaults directly — settings persist across launches with zero save/load code. In Chapter 9 a Toggle binds straight to this.
\.outdated is a key path — shorthand for { $0.outdated }. Derived lists are computed, never stored: one source of truth.

Refreshing all three managers in parallel

defer runs when the scope exits no matter how — normal return, error, early exit. Swift's "finally." The spinner can never get stuck on.
async let starts the work immediately and keeps going — all three clients run concurrently. Sequential awaits would cost brew-time + npm-time + cargo-time; this costs only the slowest one.
The single await collects all three results. gather is a tiny helper that catches each client's error so one broken manager can't sink the whole refresh.

The background check loop

[weak self] breaks a retain cycle: the store owns the task, and without weak the task would own the store right back — neither could ever be freed.
Task.sleep suspends — it holds no thread hostage while waiting, unlike Thread.sleep.
This is the "auto-update" feature, complete. The heavy lifting was already built; the feature is four lines.

One last pattern — every mutation (upgrade, uninstall, replace) wraps itself in busy-tracking so rows can show spinners:

The work parameter is a closure — a function passed as a value. Each caller hands in its own async operation; the busy-tracking and error handling are written once.

Chapter 7

The Entry Point — Living in the Menu Bar

Time to make it an actual app. In SwiftUI, an app declares Scenes rather than windows — and MenuBarExtra is a scene that lives in the macOS menu bar:

.accessory activation policy = menu bar only: no Dock icon, no entry in ⌘Tab. This is an AppKit API, which is why we need the delegate escape hatch below.
@main marks the program's entry point. No main.swift, no boilerplate — the App protocol synthesizes startup for you.
@NSApplicationDelegateAdaptor is the official bridge for plugging an old-school AppKit delegate into a SwiftUI app — needed only for things SwiftUI can't express yet.
@StateObject creates the store once and owns it for the app's lifetime. (Plain @ObservedObject here would recreate it on every re-render — a classic bug.)
.environmentObject(store) injects the store into the view tree. Any descendant grabs it with @EnvironmentObject — no passing it through every initializer ("prop-drilling").
The label is live SwiftUI: it reads @Published state, so when a background refresh finds 3 outdated packages, the menu bar badge changes to "3" by itself. No update code anywhere.
Without this, clicking the icon shows a plain dropdown menu. .window style opens a real panel that can host any SwiftUI view — lists, text fields, buttons.

Chapter 8

The UI Shell — Declarative Layout

SwiftUI is declarative: you don't mutate views, you describe the UI for the current state, and the framework redraws what changed. The panel is a vertical stack — header, tab bar, active tab, optional error banner:

@EnvironmentObject receives the store injected back in Chapter 7 — any view in the tree can declare this and get the shared instance.
@State is view-local state. Assigning to tab triggers a re-render, the switch below picks a different view, done. That's tab navigation — no controller, no notifications.
header and tabBar are private computed properties returning some View — the standard way to keep body readable instead of one 200-line expression.
The enum drives everything: the tab bar loops Tab.allCases to render buttons, this switch renders content. Add a case → the compiler points at every spot to update.

The tab bar itself is just a loop of buttons with count badges — note how the badge data comes straight from the store:

ForEach needs identifiable items — which is why Tab conforms to Identifiable. CaseIterable provides allCases.
Image(systemName:) pulls from SF Symbols — Apple's built-in library of ~6000 icons. No image assets to manage.
Views reading store.outdatedPackages re-render when it changes — so badges appear and disappear on their own as refreshes complete.
💡 Swift Concept — some View

some View is an opaque return type: "this returns one specific view type, but I'm not spelling out which." SwiftUI view types are deeply nested generics (VStack<TupleView<(…)>>…) — some View spares you from ever writing them.

Chapter 9

Feature Views — Lists, Actions, Bindings

Filtering without storing

The Installed tab filters as you type — and the filtered list is computed, never stored. Derive, don't duplicate:

Each keystroke updates filter → body re-evaluates → filtered recomputes → the list updates. Zero "search logic" wiring.
$filter passes a Binding — a two-way read/write connection. The text field writes into our @State as the user types. The $ prefix on any @State/@AppStorage property produces its binding.
List + Identifiable items = done. This is why Package.id exists (Chapter 2).

The Issues tab — deprecation handling

The feature this app exists for. Each deprecated/disabled package shows its reason and the available actions:

if let inside a view body: the Text simply doesn't exist when there's no reason. Conditional UI is just Swift control flow.
The busy pattern pays off: while the store's perform() holds this package's id in busyPackageIDs, the buttons are replaced by a spinner. When defer removes the id, the buttons come back.
Button actions are synchronous, so async work is wrapped in Task { … } — fire the operation and let the published state drive UI updates. Recall replace installs the successor before uninstalling the old tool, so you're never left with neither.
role: .destructive tells macOS this action deletes something — it renders red automatically. Semantic styling beats hard-coded colors.

Settings — bindings all the way down

The payoff of @AppStorage from Chapter 6: this toggle reads and persists the setting with no save/load code anywhere. Flip it, quit, relaunch — still flipped.
onChange reacts to the value changing: picking a new interval cancels the old background task and starts one with the new cadence.

Build, Run, Ship 🚀

Compile an optimized binary and launch it:

A 📦 appears in your menu bar. When packages are outdated it shows a count; when something is deprecated, a ⚠︎ count joins it. To launch it at login, install the LaunchAgent from README.md.

Exercises — make it yours

  3. Pinning. Let users exclude packages from "Update All." Hint: persist a Set<String> of pinned ids.
